ユーザーと作品設定の打ち合わせを行い、結果を canon ファイル群に書き起こす。これは novelist の要のコマンドであり、**ここで書き起こした canon だけが後段の全工程(執筆・監査・lint)の判断基準になる**。会話にしか残っていない設定は存在しないのと同じ、という前提で進める。

# 進め方の原則

- **質問は AskUserQuestion で、1回に1〜3問まで。** 一度に大量に聞かない。ユーザーの回答から次の質問を組み立てる、本物の打ち合わせにする。
- **想像で埋めない。** ユーザーが決めていない箇所は、選択肢を提案して選んでもらう(お任せと言われた場合のみ提案内容で確定し、確定内容を必ず見せる)。
- **フェーズが終わるたびに即ファイルへ書く。** 全部聞き終えてからまとめて書かない(会話が長引くと文脈から落ちるため)。書いたら要点をユーザーに見せて確認を取る。
- 既に canon に内容がある場合は読み込んで「決まっていること」を要約し、空欄・矛盾だけを聞く(再実行・途中再開に対応)。
- $ARGUMENTS があれば、その指示(再開位置・補足)に従う。

# フェーズ

## 1. 作品コンセプト → `canon/world.yaml` (title/genre/target_reader/summary)
ジャンル、想定読者・レーベル感、長さ(短編/長編・章数の目安)、一言コンセプト、結末の方向性(ハッピー/ビター等)。

## 2. 世界観 → `canon/world.yaml` (setting/rules/banned_words)
時代感・技術水準・魔法や超常の有無とそのルール・地理・社会制度。
**必ず聞くこと**: 「この世界に存在してはいけない語」(現代語・技術用語など)→ banned_words に登録。これは保存のたびに機械検出される。

## 3. 文体・作風 → `canon/style.yaml`
人称と視点ルール、時制、トーン、参考にしたい作風、地の文で禁止したい表現。
**必ず聞くこと**:
- **専門描写の深さ**(→ `expertise_policy`): 舞台に大学・職業・専門領域が含まれるなら、「講義や専門の内容をどこまで具体的に書いてよいか」を確認する。AI はデフォルトで「それっぽく」書く癖があり、本職の読者には違和感になる。迷ったら「疑似専門性は禁止」を推奨する
- **定量ルール**(→ `quantitative`): 台詞の読点上限・文末「った。」の連続上限のデフォルト値を見せ、好みに合わせて調整する(lint が機械検出する)

## 4. キャラクター → `canon/characters/<id>.yaml` (1人1ファイル)
主要キャラから1人ずつ。各キャラで:
- 名前(正典表記)・別名/呼び名 → aliases。読み間違えやすい/揺れやすい表記は `canon/glossary.yaml` の variants にも登録
- 不変属性(目・髪・利き手・特徴)→ invariants。**事故りやすい属性(目の色など)は lint.forbid の正規表現も併せて書く**
- 口調 → speech。一人称・二人称・敬語レベル・口癖。**台詞例を2〜3個、ユーザーと一緒に作って examples に入れる**(口調監査の最重要参照になる)。台詞例の基準は「**普通の人が普通に言う言葉**」— 性質を宣言する決め台詞(「〜だけは覚えておいてほしい」型)を提案しない。性質は普通の会話の結果として現れる形にする
- **性格の設定語には必ず「否定形」と「具体例」を付ける**(→ speech.never / speech.episode)。「正直すぎる」「ロジカル」のような形容だけでは、AI が辞書的な意味(正論を主張する人・分析家の語彙)で実装してズレる。「この性格の人が**やらない**こと」(断言口調、正論語彙など)と、性格が現れる具体エピソード(例: 「変なTシャツやな」と面白半分で言ったら実は誕生日プレゼントだった)を聞き出して登録する
- 背景・目的・人間関係
- **1行 summary を必ず書く**(全章で常時ロードされる要約。表記・生死・立場・特筆能力を圧縮)

## 5. 制約(禁じ手)の洗い出し → `canon/constraints.yaml` 【最重要・スキップ禁止】
キャラと世界観が出揃ったら、設定を「展開を縛る制約」に変換する。各強い能力・ルール・立場について次を聞く:
> 「この設定が存在すると、成立しなくなる展開は何ですか?」
> (例: 嘘を見抜けるキャラがいる → その同席場面で騙しは成立しない)
回答を**否定形のルール**(rule)+**発動条件**(holds_while)で登録する。移動手段の制約(即日移動できる範囲)、蘇生・治癒の限界、身分制度による行動制限もここで確認する。

## 6. 用語集の仕上げ → `canon/glossary.yaml`
ここまでに出た固有名詞(人名・地名・組織・アイテム)を全部 canonical で登録。ユーザーに「他に固有名詞はあるか」を確認。

# 保留の扱い

ユーザーが「あとで決める」と言った項目は、空欄のまま `# PENDING: ユーザー保留(理由)` コメントを付けて記録する。PENDING の付いた項目は canon-sync が自動確定しない。

# 終了時

1. canon 全体を読み直し、**内部矛盾がないか自己チェック**して結果を報告する。
2. 決定事項のサマリをユーザーに提示する。
3. 次のステップとして `/novelist:outline`(章構成の設計)を案内する。
